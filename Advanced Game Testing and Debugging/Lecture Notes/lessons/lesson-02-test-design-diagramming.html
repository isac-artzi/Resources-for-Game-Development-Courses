Test Design and Diagramming

Topic 1 taught you to recognize a defect. This one teaches you to write it down so that a stranger can reproduce it, a tracker can route it, a duplicate detector can find it, and a test can be designed from it — before anyone writes the code that breaks.

Reading: Modern Game Testing ch. 6–8 + 6 papers Assignment: Benchmark — Bug Reporting and Workflow · 100 pts · due Sep 27 Sessions: 3–6 Est. time: 150 min + reading

By the end you will be able to

  1. Utilize an issue-tracking system to track bugs — fields, workflows, categories, and status transitions, not just the "Create" button.
  2. Analyze the entire life cycle of a bug as a state machine, and say what each transition obligates someone to do.
  3. Utilize automated tools to identify and track bugs, including duplicate detection and evidence capture.
  4. Explain the importance of reproducibility in debugging, and write repro steps that survive a stranger, a continent, and 2 a.m.
  5. Apply data-driven testing methodologies — equivalence partitioning, boundary values, decision tables, state-transition diagrams — to produce test tables rather than test guesses.

1A bug report is a program that a human executes

Everything you write in a tracker is read by someone who was not there. That person has a different build, a different machine, a different mental model of the feature, and eleven other tickets open. Your report is the only interface between what you saw and what they will do about it. Treat it as an interface and the standard rules of interface design apply: predictable structure, no ambiguity about who does what, and every field carrying information the caller actually needs.

The costs of getting this wrong are boring and enormous. An engineer who cannot reproduce your defect in the first ten minutes will either come back to you for clarification — a round trip that in a distributed team costs a working day — or close the ticket as Cannot Reproduce, which puts the defect back into the build with a paper trail claiming it isn't there. Neither outcome involves the bug getting fixed. Both outcomes were determined by how you wrote three or four fields.

The title is a search key, not a sentence

Titles get used in ways new testers never anticipate: scanned in a list of 200 during triage, typed into a search box by someone checking whether the bug is already filed, matched by an automated duplicate detector, pasted into a release-notes draft, and read aloud in a meeting. All five of those uses reward the same thing — distinctive, front-loaded, searchable vocabulary — and all five punish narrative.

PAL is the format this course requires: Problem, Action, Location, in that order, separated by em dashes or commas. The problem comes first because a triage lead scanning a list is scanning for consequences. The action comes second because that is the search term another tester will use when they hit the same thing. The location comes last because it disambiguates: the same problem in two places is two bugs.

TitleVerdict
Game crashesUseless. Matches every crash ticket in the database and discriminates none of them. Guarantees a duplicate.
Bug in the save system!!Useless. "Bug" is the one word that appears in 100% of records. Punctuation is not severity.
When I was in the cargo bay and I quicksaved during the elevator, my save wouldn't loadContent is right, form is wrong. Narrative, first person, 96 characters before the consequence appears. Unscannable in a list.
Save file fails to load — quicksaving during elevator transition — Cargo Bay BPAL. Problem, action, location. Searchable on "quicksave", "elevator", "Cargo Bay B", or "save file fails to load".
Frame time spikes to 61 ms — first grenade detonation after level load — Ruined WardPAL with a number. The number turns a subjective report into a measured one and makes the fix verifiable.
Why the title format is a duplicate-prevention mechanism

Zhang and colleagues (2023), reviewing the state of duplicate bug report detection, examine how far automated detectors have actually come — and the honest summary is that the techniques that work in practice still lean heavily on textual similarity between reports. That has a direct consequence for you: a detector, and a human using a search box, can only match on the words you chose. Two testers who both write "Game crashes" produce two records with no distinguishing vocabulary; a detector will either flag them as duplicates of each other and of forty unrelated crashes, or flag nothing. Two testers who both write PAL titles converge on the same rare tokens — "quicksave", "elevator", "Cargo Bay B" — and the match is unambiguous. You are not writing prose. You are writing the index.

Second-person imperative repro steps

Repro steps are instructions, so write them in the mood that language reserves for instructions: second-person imperative. "Launch the game." "Load the Cargo Bay B checkpoint." "Press F5 while the elevator is between floors." Not "I launched the game", not "the game was launched", not "you should probably be in the cargo bay first".

This is not style pedantry, and it is worth being precise about why:

  • Imperative removes the actor ambiguity. "The elevator was activated" leaves open whether the tester pressed the button, an NPC did, or a script fired. The reader has to guess, and half of them guess differently from you.
  • Past-tense narrative encodes an unrepeatable session. "I had been playing for about an hour" is not a step anyone can follow. If the hour matters, it is a precondition with a number: "Play for at least 45 minutes, or load the attached save with a 47-minute session timer."
  • Imperative forces atomicity. It is hard to write two actions in one imperative clause without noticing you have done it. "Open the menu, equip the rifle and quit" is three steps, and the bug might only need two of them.
  • Conditionals expose missing information. The moment you write "if you're lucky", you have discovered that your repro rate is not 100% and you owe the reader a number.
Why the mood matters at 2 a.m. on another continent

Do the arithmetic on a co-development studio. Your outsourced QA partner is eleven time zones away; a question you ask at 4 p.m. gets answered while you sleep and lands at 9 a.m. the next day. Each clarification round trip is therefore a calendar day, not five minutes. Suppose 40 tickets a week and an ambiguity rate of 25% — ten tickets a week each losing a day of engineer attention. That is two engineer-weeks per month spent on the reconstruction of information that the reporter already had and did not write down. Nobody schedules that time, and it comes out of the fix budget.

Expected and Actual are two fields for one reason

Expected is where you name the oracle from Topic 1. Actual is where you record the observable. Keeping them separate does something a single "description" field cannot: it makes the disagreement explicit, which is the only thing that makes the ticket arguable on evidence instead of on authority. If your Expected field cannot cite a requirement, an acceptance criterion, a cert rule, or a defensible implicit standard ("a save file the game wrote must load"), you have found the more interesting problem, and it is a spec gap.

Both fields should be falsifiable. "Expected: it works correctly" is not falsifiable. "Expected: the checkpoint loads to the elevator lobby with inventory intact, per REQ-SAVE-014" is. "Actual: it breaks" is not. "Actual: loading screen completes, player spawns at world origin (0,0,0) under the level geometry, falls for 3.2 s, respawn never triggers" is.

The timing window is the bug, so the timing window is in the step. "Press F5 during the transition" would leave a reader pressing it at the wrong moment and reporting Cannot Reproduce. Giving the approximate offset, and saying what visual event to count from ("after the doors shut"), turns a race condition into an instruction. Expected cites the oracle by identifier. REQ-SAVE-014 is a requirement someone agreed to, so this ticket is no longer one tester's opinion about how saving ought to work. It also creates the traceability link we build in section 7: requirement → test case → defect. 16
Actual: Load completes; player spawns at (0,0,0) below terrain; falls 3.2 s; no respawn.
Actual is observable and quantified. Coordinates and a duration, not "the level is broken". The (0,0,0) detail is worth more than the rest of the sentence combined: spawning at world origin is the signature of a transform that was never written or was written as default, which points the engineer at serialization rather than at level geometry. Good Actual fields do diagnostic work for free.
17
Repro rate: 9/10 attempts (build 0.7.3-rc2); 0/10 with quicksave pressed after doors open.
A rate, out of a stated number of attempts, plus a negative control. "Intermittent" is not a rate. 9/10 tells triage this is deterministic enough to schedule and tells the fixing engineer they will see it on the first try. The negative control — the variation that does not fail — is the most under-used field in bug reporting: it halves the search space before anyone opens a debugger, and it is the difference between a report and an experiment.
18
Attachments: repro.mp4 (frame counter), Player.log (lines 4120–4180), cargo_b_pre.sav, post_bug.sav
Evidence, with the log lines already narrowed. Attaching a 40 MB log unread is not evidence, it is homework you assigned to someone else. Citing the line range says you looked. Both saves matter: the pre-state so the engineer can reproduce, the post-state so they can inspect the corrupted artifact directly — that file is the defect, in hexadecimal.
19
Notes: First seen in 0.7.3-rc1 (CI #1802). Not reproducible in 0.7.2. Suspect PR #614 (async save).
A bisection result and a hypothesis, clearly labelled as a hypothesis. "Not reproducible in 0.7.2" is the single most valuable sentence in the ticket: it turns an open-ended search into a diff of 39 CI builds. Naming a suspect PR is fine as long as you label it a suspicion — being wrong costs nothing, and being right saves an afternoon. What you must not do is state the cause as fact in the Actual field; that is how a wrong hypothesis gets inherited by three later tickets.

Capturing the evidence, per engine

The attachment list above assumes you can actually produce those artifacts on demand. Both engines will give them to you; neither will do it by default.

Making a Unity build self-reporting

  • Stamp the build. Write the CI build number and commit SHA into Application.version or a generated BuildInfo ScriptableObject at build time, then render it in the corner of the pause menu in every non-shipping configuration. A build ID a tester has to ask for is a build ID that ends up missing from the ticket.
  • Know where the log lives. Player.log on Windows sits under %USERPROFILE%\AppData\LocalLow\<Company>\<Product>\; on macOS under ~/Library/Logs/. Put that path on a slide for your team, because 90% of "I couldn't find the log" is people not knowing this.
  • Capture on a key. ScreenCapture.CaptureScreenshot plus a Debug.Log of the current scene, position, seed, and time-since-load, bound to one key, produces a matched screenshot/log pair with no tester discipline required. The Unity Recorder package does the same for video.
  • Log the RNG seed at session start — the Topic 1 rule, cashed in here. A report that carries the seed converts a 1-in-40 defect into a deterministic one.
  • Unity Cloud Diagnostics collects crashes and exceptions from playtesters automatically, with stack traces and device metadata. It will not write your repro steps, but it tells you which defects are worth chasing.

In the Editor, Application.consoleLogPath returns the active log path at runtime — print it in your debug overlay and testers can copy it.

Making an Unreal build self-reporting

  • Stamp the build. FApp::GetBuildVersion() and the engine's BuildSettings give you a version string; surface it with a debug HUD or a UE_LOG at startup. Launch with -log to get a live console window in a development build.
  • Know where the log lives. <Project>/Saved/Logs/<Project>.log, with the previous run rotated to a timestamped backup. Crash artifacts land in Saved/Crashes/ and are what the Crash Reporter uploads.
  • Capture on a key. The HighResShot 2 console command writes a screenshot to Saved/Screenshots/; stat unit and stat fps overlay the frame timings you will need for any performance ticket; DumpConsoleCommands and obj list capture state.
  • Log with categories. DECLARE_LOG_CATEGORY_EXTERN(LogSaveSystem, Log, All) and then UE_LOG(LogSaveSystem, Warning, TEXT("Quicksave requested during transition")) means your attached log excerpt can be filtered to the subsystem instead of pasted whole. -LogCmds="LogSaveSystem Verbose" raises verbosity for one run without a rebuild.
  • Session Frontend → Automation stores test artifacts and screenshots from automated runs; those are attachable evidence too, and they carry the build metadata already.

Blueprint-only teams: Print String with Print to Log enabled still lands in the same file, and the Blueprint debugger's breakpoint-and-watch values are screenshot-able evidence.

    Video is genuinely valuable and belongs on the ticket. But a video of an intermittent defect shows that it happened once — which nobody disputed. Attach the video and write the rate; if you can only do one, write the rate.

    2The bug life cycle is a state machine, and every edge has an owner

    Trackers present the life cycle as a list of statuses, which makes it look like a form field. It is not a form field. It is a finite state machine, and the reason to draw it as one is that a state machine forces you to answer three questions per edge that a dropdown lets you skip: what has to be true before this transition is legal, who is obligated to act once it fires, and what typically goes wrong here.

    Cannot Reproduce is a process failure, not a verdict

    CNR does not mean the defect does not exist. It means two configurations disagreed and nobody found out why. Every CNR closure should be read as an unanswered question: which of build, platform, hardware, settings, save state, timing, RNG seed, or account state differed between the reporter's machine and the fixer's? A team with a rising CNR rate does not have unusually careless testers; it has a tooling gap — no seed logging, no build stamping, no save-file attachment, no repro-rate discipline. The single most useful metric in this section is the ratio of CNR closures to total closures, and the correct response to it climbing is to fix the evidence pipeline, not to lecture the testers.

    Two transitions are more dangerous than the rest and deserve naming. Fixed → Closed without verification is the one that puts defects back in the build; "Fixed" is a claim by the person with the strongest incentive to believe it and the least ability to be objective about it. Reopened is the one that carries information: a reopen rate above roughly one in ten fixes is usually telling you that fixes are being written against symptoms rather than root causes, which is the Topic 1 lesson resurfacing as a workflow metric.

    Why a status transition should be hard to fake

    Neville-Neil's "Four Horsemen of an Ailing Software Project" (2022) is a catalogue of the ways teams substitute the appearance of progress for progress. A workflow is one of the places that substitution happens most easily: if anyone can move a ticket to Fixed, and Closed follows automatically after a week, your database converges on a comforting number of open defects that has no relationship to the state of the build. Configure the tracker so that Closed requires a verification build ID, that Won't Fix requires a rationale field, and that CNR requires the number of attempts and the platform tried. Fields that are mandatory at the transition are the cheapest process enforcement that exists, and unlike a policy document, nobody can forget them.

    Your team's dashboard shows 140 tickets closed this month, a record. It also shows 31 of those closures were Cannot Reproduce and 18 were reopens of tickets closed the previous month. What is the most defensible reading?

    Why the third option: 31 CNR plus 18 reopens is 49 of 140 closures — 35% — that either never established what happened or established it wrongly. The closure count went up precisely because those two exits are cheap. CNR points at the evidence pipeline (seeds, build stamps, save files, repro rates); reopens point at fixes verified by their authors or written against symptoms. Both are fixable, and neither is fixed by celebrating the 140.
    Why "throughput is up" is tempting
    It is the reading the dashboard is designed to produce, and closure count is the metric most trackers put on the front page. That is exactly why it deserves suspicion: a metric that rises when you do the easy thing will eventually be optimized by doing the easy thing.
    Why gatekeeping filing is tempting
    It would reduce CNR — by suppressing reports, including true ones, and by doubling the cost of filing at the exact moment you want more evidence, not less. Fix the reproduction problem at its source: log seeds, stamp builds, attach saves, and record repro rate out of N.

    3Duplicates, and why your title decides whether they happen

    Duplicate reports are not a filing annoyance. They split evidence across records so that no single ticket looks serious enough to schedule, they cause the same defect to be triaged three times by three people, and they corrupt every count you might want to draw a conclusion from. Zhang and colleagues (2023) survey where automated duplicate detection actually stands and find the field is less solved than the published accuracy numbers suggest — which means the practical burden stays with the person writing the title.

    In your tracker, this week

    Before you file anything for the Benchmark assignment, search the existing project backlog using the two or three rarest words from your proposed title, not the whole sentence. Search engines in Jira, Trello, and Bugzilla all do term matching; feeding them a full sentence dilutes the query with common words. If you find a match, do not close yours silently — link it as a duplicate and move any evidence the original lacks (your save file, your repro rate, your platform) onto the original. A duplicate that donates evidence has done more for the project than a fresh ticket.

    4Test design: choosing the few inputs that matter

    So far this lesson has been about defects you already found. Test design is the other direction: deciding what to try, before you know what is broken, in a way that is defensible when someone asks why you tested those twelve values and not the other four thousand. The techniques below are old, boring, and unreasonably effective, and almost no student project uses any of them.

    Equivalence partitioning

    Group inputs into classes whose members the system should treat identically, then test one representative per class. If stamina is valid over 0–100, then 37 and 62 belong to the same class and testing both buys you nothing. The partitions that matter are the ones you would not have thought to write down: negative stamina, stamina above the cap, stamina as a non-number if the value comes from a config file or a network packet, and the "no value at all" case.

    The technique's real payoff is that it makes your omissions visible. Once you have written the partitions in a table, a reviewer can point at the missing row. Without the table, the missing row is invisible to everyone including you.

    Boundary value analysis

    Defects cluster at the edges of partitions, because edges are where humans write < when they meant <=, where clamping is applied on one side and forgotten on the other, and where a float comparison stops behaving like arithmetic. If you test only one value per partition, test the boundary; if you can afford three, test just-below, at, and just-above. In a game the boundaries are everywhere and are rarely documented: max stack size, level cap, currency ceiling, the frame at which a coyote-time window closes, the exact HP where a low-health shader kicks in, the last save slot, the 100th inventory item.

Discovering the same ambiguity during certification costs a submission.

    State-transition diagrams

    Games are state machines pretending to be worlds. Every character controller, quest, matchmaking flow, and save system is a set of states with legal transitions, and the defects live in the transitions nobody drew. Draw the diagram, then test it three ways:

    • Valid transitions (0-switch coverage) — every arrow in your diagram is exercised at least once. This is the minimum and most teams stop here.
    • Transition pairs (1-switch coverage) — every legal pair of consecutive transitions. This finds the bugs where a state is entered correctly from A and incorrectly from B.
    • Sneak paths — attempt the transitions that are not in the diagram: quicksave while dying, open the inventory during a cutscene, disconnect mid-purchase, pause during the death animation. This is where softlocks live, and it is the only one of the three that requires imagination rather than bookkeeping.

    The elevator save bug annotated earlier is a sneak path: Transitioning was never considered a state in which Quicksave could be requested, so nothing wrote the player transform. Drawing the diagram before writing the save system would have surfaced the empty cell in about ninety seconds.

Pairwise testing — the technique for when the grid has twelve dimensions instead of two — is the natural next step, and Topic 5 develops it properly with covering arrays. For now the point is that these tables are the artifact your Benchmark deliverable should show alongside the bug reports: they demonstrate that the defects you filed came from a design, not from wandering.

    Data-driven test tables

    Once the cases are in a table, the worst thing you can do is hand-write one test function per row. Data-driven testing keeps the data in a table and the logic in one place, so adding a case is a one-line change and every case gets the same assertions. Start with the table as data — this is the artifact you can share with a designer, who will happily argue about the numbers and never about your test code:

    stamina_cases.yaml — the test table as data
    # Parameter under test: PlayerStamina.Set(value) — REQ-MOVE-031
# Policy: clamp to [0,100]. Generated from boundary analysis, reviewed by design 9/18.
cases:
  - id: below_min_far    input: -50     expect: 0     partition: invalid_low
  - id: below_min_edge   input: -1      expect: 0     partition: boundary_low
  - id: at_min           input: 0       expect: 0     partition: boundary_low
  - id: above_min        input: 1       expect: 1     partition: valid
  - id: nominal          input: 50      expect: 50    partition: valid
  - id: below_max        input: 99      expect: 99    partition: boundary_high
  - id: at_max           input: 100     expect: 100   partition: boundary_high
  - id: above_max        input: 101     expect: 100   partition: invalid_high
  - id: nan              input: .nan    expect: unchanged  partition: special

    Both engines have first-class support for driving a test from a table. The two panes below implement the same nine cases.

    Unity Test Framework is NUnit, so [TestCase] attributes give you a table with per-row names in the Test Runner. Each row appears as its own result, which matters: a failing row tells you which boundary broke without opening the log.

    StaminaBoundaryTests.cs — EditMode
    using NUnit.Framework;

[TestFixture]
public class StaminaBoundaryTests
{
    // value           expected   name shown in the Test Runner
    [TestCase(-50f,   0f,   TestName = "below_min_far")]
    [TestCase( -1f,   0f,   TestName = "below_min_edge")]
    [TestCase(  0f,   0f,   TestName = "at_min")]
    [TestCase(  1f,   1f,   TestName = "above_min")]
    [TestCase( 50f,  50f,   TestName = "nominal")]
    [TestCase( 99f,  99f,   TestName = "below_max")]
    [TestCase(100f, 100f,   TestName = "at_max")]
    [TestCase(101f, 100f,   TestName = "above_max")]
    public void Set_ClampsToValidRange(float input, float expected)
    {
        var s = new PlayerStamina(max: 100f, current: 50f);  // plain C#, no scene
        s.Set(input);
        Assert.That(s.Current, Is.EqualTo(expected).Within(0.0001f));
    }

    [Test]
    public void Set_NaN_LeavesValueUnchanged()          // the special case
    {
        var s = new PlayerStamina(max: 100f, current: 50f);
        s.Set(float.NaN);
        Assert.That(s.Current, Is.EqualTo(50f));   // NaN must never reach the model
    }
}

    Is.EqualTo(expected).Within(0.0001f) is not decoration: comparing floats with == is the precision defect from Topic 1, and it belongs in a test even more than in gameplay code, because a test that fails intermittently on the last bit trains the team to ignore red. Note also that PlayerStamina is a plain class, not a MonoBehaviour — that seam is what lets these nine cases run in milliseconds in EditMode, and it is the subject of Topic 3.

    Unreal's Automation framework gives you the same shape. A complex automation test enumerates its own parameter list via GetTests, so each row appears separately in the Session Frontend and can be run individually from the command line.

    StaminaBoundaryTest.cpp
    // One entry per boundary case: {input, expected, name}
static const TArray<TTuple<float, float, FString>> StaminaCases = {
    { -50.f,   0.f, TEXT("below_min_far")  },
    {  -1.f,   0.f, TEXT("below_min_edge") },
    {   0.f,   0.f, TEXT("at_min")         },
    {   1.f,   1.f, TEXT("above_min")      },
    {  50.f,  50.f, TEXT("nominal")        },
    {  99.f,  99.f, TEXT("below_max")      },
    { 100.f, 100.f, TEXT("at_max")         },
    { 101.f, 100.f, TEXT("above_max")      }
};

IMPLEMENT_COMPLEX_AUTOMATION_TEST(FStaminaBoundaryTest,
    "Project.Gameplay.Stamina.Boundaries",
    EAutomationTestFlags::EditorContext | EAutomationTestFlags::EngineFilter)

void FStaminaBoundaryTest::GetTests(TArray<FString>& OutBeautified,
                                    TArray<FString>& OutCommands) const
{
    for (int32 i = 0; i < StaminaCases.Num(); ++i)
    {
        OutBeautified.Add(StaminaCases[i].Get<2>());   // readable row name
        OutCommands.Add(FString::FromInt(i));           // row index as the command
    }
}

bool FStaminaBoundaryTest::RunTest(const FString& Parameters)
{
    const int32 Index = FCString::Atoi(*Parameters);
    const auto& Case = StaminaCases[Index];

    FPlayerStamina Stamina(/*Max=*/100.f, /*Current=*/50.f);
    Stamina.Set(Case.Get<0>());

    TestNearlyEqual(Case.Get<2>(), Stamina.GetCurrent(), Case.Get<1>(), 0.0001f);
    return true;
}

    Run the whole table headless with UnrealEditor-Cmd.exe Project.uproject -ExecCmds="Automation RunTests Project.Gameplay.Stamina; Quit" -unattended -nullrhi, which is precisely the command your CI will use in Topic 3. If you prefer the BDD style, the same table drops into a DEFINE_SPEC block with a for loop around It(...) — one It per row, same result.

    Your inventory holds 100 items. You have time to run four tests on the "add item" path. Which four?

    Why the second set: 0, 99, 100, and the stackable-at-full case are the boundary and the one combination where two conditions interact. 25, 50, and 75 are all the same equivalence class as each other — if adding to a 25-item inventory works, adding to a 50-item one exercises identical code. The fourth case is the decision-table insight: "full" and "stackable" together produce behavior that neither condition produces alone, and it is the case that duplicates items in a live build.
    Why even spacing is tempting
    It looks like coverage and it is easy to justify in a status update. It systematically avoids the boundaries, which is where the off-by-one lives. Even spacing is what you do when you have not decided what a partition is.
    Why stress testing is tempting
    Stress is a real and necessary trigger — it is one of the six defect triggers in Topic 3. But with only four tests, spending all of them past the boundary tells you nothing about whether the boundary itself is correct, and "it broke at 500" is not actionable if you never established that 100 works.

    5Traceability: requirement → test case → defect

    Three artifacts, two links, and a discipline that takes about five minutes a week. Each requirement has at least one test case; each test case has an identifier; each defect names the requirement and the test case that caught it, or notes that no test case existed — which is itself the finding.

    RequirementTest caseTechniqueDefectStatus
    REQ-SAVE-014 Quicksave restores position and inventoryTC-SAVE-014-a quicksave while groundedState transition, valid—Pass
    REQ-SAVE-014TC-SAVE-014-b quicksave mid-elevatorState transition, sneak pathSTRAY-2291Open S0

    The last row is the reason the table exists. A requirement with no test case is invisible in every other view of the project: it does not appear in a pass rate, it does not appear in a bug count, and it will not appear in anyone's memory during a release meeting. One column of "none" entries is a more honest coverage report than any percentage.

    Traceability also runs backwards, and that direction is the one that pays during a live incident. When a defect arrives from players, the link tells you which requirement it violates, which test should have caught it, and therefore whether you have a code defect or a test-design defect. Those two have different fixes. Every escaped defect should end with a new or corrected test case, named in the ticket — otherwise the same class of bug escapes again with a different symptom.

    6Metrics that help, and metrics that rot a team

    Once your tracker is well-structured, it becomes a measurement instrument, which is where the danger starts. Phillips (2022), writing on measuring agile project performance, and Neville-Neil (2022) on ailing projects both circle the same failure: teams measure what the tool reports rather than what they need to know, and then people optimize the report. Any metric attached to individual performance stops measuring the thing and starts measuring the incentive.

    MetricWhat it tells youVerdict

    Why per-person counts are worse than no metric

    Suppose a lead announces that testers are measured on tickets filed. The rational response is to file the same texture seam eleven times, once per room. Ticket count rises, duplicate rate rises, triage time rises, and the hard defect — the intermittent desync that would have taken two days of focused investigation and produced one ticket — never gets looked at, because investigating it costs the tester their standing. Nothing in that chain requires anyone to act in bad faith. The metric did all of it. Measure the system (escaped defects, CNR ratio, time in state); never measure the individual with a number that the individual controls directly.

    Which pair of numbers best tells a producer whether the project's QA is working?

    Why the third pair: escaped defects by severity answers "is the testing system catching what matters before players do", and it cannot be improved by filing or closing more tickets. Median time in state answers "where does work actually stall", and it points at a structural fix — a queue, a missing owner, a verification bottleneck — rather than at a person. Together they cover outcome and process without creating an incentive anyone can game cheaply.
    Why open/closed counts are tempting
    They are on the tracker's default dashboard and they move every day, which makes them feel like a pulse. Both are dominated by filing and closing policy: a triage sweep that bulk-closes stale S3s produces a spectacular week and changes nothing about the build.
    Why test count and coverage are tempting
    They sound rigorous and they are easy to automate into a report. Both measure the volume of testing rather than its yield, and both are trivially inflated. A suite of 900 tests that never touches the save system is worse than 40 tests that do, because it produces confidence.

    7The bug won't reproduce — what now?

    This is the highest-frequency hard moment in the job, and the difference between a junior and a senior tester is almost entirely what happens in the next twenty minutes. The tree below is the order of operations that costs the least: cheap, high-yield checks first, machine-borrowing last. Work it against a real defect from your own project before Session 4.

    Why the first question is about the build, not the bug

    Because it is free and it is right often enough to pay for itself many times over. Two people disagreeing about whether a defect exists while running different builds is the most common non-defect in QA, and it burns an hour every time. Verifying the build ID and the platform before investigating anything else is the reproducibility equivalent of checking that the machine is plugged in — slightly insulting, frequently correct.

    Reading list with a specific question to answer for each

    • Andrew (2024), "Maximize Efficiency with the Perfect Ticket Template in Jira." Practical and opinionated. Question: build the template for your Benchmark project, then list three fields you added that the article does not mention and justify each with a defect you have actually seen.
    • Gorton (2022), "Trello vs Monday.com." A tool comparison, useful for the criteria rather than the verdict.     • Zhang et al. (2023), "Duplicate Bug Report Detection: How Far Are We?" Question: given what they find about textual-similarity approaches, what does that imply about the way you should phrase a title? Answer it in one concrete rule you can apply to every ticket you file.

    Bring to the assignment

    Benchmark — Bug Reporting and Workflow · 100 points · due Sep 27 · three bug reports in PAL format entered into a live tracker, plus a 3–5 minute video. Assesses competency 1.5: Apply data-driven testing methodologies and bug tracking to determine defects in game software.

    Every section of this lesson maps onto a piece of that deliverable. Arrive with:

    • Three defects, each with a PAL title — problem, action, location. Run each title through the Duplicate Detector logic by hand first: what are its two rarest, most discriminating terms? If you cannot name them, rewrite the title.
    • Repro steps in second-person imperative, one action per line, preconditions listed separately, and any timing window stated with a number. Read them aloud; every line must be a command you could give a person at the keyboard.
    • Expected and Actual as separate fields, Expected citing a requirement identifier or an explicitly stated implicit standard, Actual quantified and observable.
    • Repro rate out of N attempts, plus one negative control — the variation that does not fail. Run it ten times and write the number down. This single field is what separates the A reports from the B reports.
    • Attachments as evidence: video, log excerpt with the line range cited, save file, build ID, commit SHA, platform, GPU/driver, OS, and the RNG seed if the system uses randomness. Use the per-engine capture list in section 1 to make these available before you start testing, not after.
    • Severity and priority set separately, with a one-line justification for each. At least one of your three should have severity and priority that diverge; explain why in the video.
    • A configured workflow, not a default one: show your status transitions, who owns each state, and at least two mandatory fields you added at a transition (for example, a verification build ID required to reach Closed, and an attempts-and-platform note required to reach Cannot Reproduce). Demonstrate a real transition on screen, including one ticket you deliberately move to Reopened.
    • One test-design artifact — a boundary table, a decision table, or a state-transition grid — for the feature one of your defects lives in, with the empty cell or missing partition circled. This is the "data-driven testing methodologies" half of the competency, and it is the part students most often skip.
    • A traceability row for each defect: requirement → test case → defect. If no test case existed, say so on camera. That admission scores better than an invented one.
