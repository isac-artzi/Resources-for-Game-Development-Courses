Memory Management in Games

Frame time degrades. Memory does not. When you run out you do not get a slower game — you get a crash report, a certification failure, or a process the operating system kills without asking. This topic is about seeing that ceiling coming, and proving with numbers that you moved it.

Reading: Hizon et al. (2002) + 3 papers Assignment: Memory Optimization · 100 pts · due Nov 22 Sessions: 19–22 Est. time: 130 min + reading

By the end you will be able to

  1. Evaluate memory-related issues — leaks, retention, fragmentation, churn — and quantify their performance impact rather than describing it.
  2. Apply memory management techniques: pooling, fixed-size allocators, segregated heaps, streaming budgets, and allocation-rate discipline.
  3. Use tools that track allocation, deallocation, and fragmentation in both engines, with snapshot diffing as your primary method.
  4. Develop cross-platform prevention strategies that survive the jump from a 32 GB desktop to a 4 GB phone or a fixed-budget console.
  5. Balance memory optimization against gameplay and visual quality, and defend the trade in a design conversation.

1Memory is a cliff, not a slope

Topic 4 taught you to treat 16.6 ms as a currency you spend. Overspend it and the game gets worse in a way players can feel but survive: 55 fps instead of 60, a hitch on a corner, a soft complaint in a review. Memory does not work like that. A memory budget is a wall. You are under it or you are not, and the failure at the wall is discontinuous — an allocation returns null, a texture fails to stream in and renders as a magenta placeholder, the console's fixed partition refuses the request, or the mobile OS low-memory killer terminates your process between two frames with no callback you can usefully handle.

That discontinuity is why memory bugs are the ones that ship. A frame-time regression shows up on every machine that runs the benchmark scene. A memory regression shows up only on the machine with the smallest budget, in the session that ran longest, after the player did the thing your test plan never did — usually "played for two hours without returning to the main menu." Your desktop has 32 GB and a page file; it will absorb a 400 MB leak for the entire development cycle and never say a word. The phone will not.

Why the ceiling is lower than the spec sheet says

Students size their budget from the device's advertised RAM. Nobody gets that. On a current console, a chunk of physical memory is reserved for the system, and what remains is further split between CPU-visible and GPU-visible pools with hard boundaries. On a 4 GB Android device the OS, the launcher, and background apps are already resident; a game that exceeds roughly a third to a half of physical RAM is in the low-memory killer's sights, and on iOS the jetsam limit is a documented fraction of device RAM. So a "4 GB phone" is often a 1.5 GB game. Write your budget as an absolute number of megabytes per platform, in a document, before you profile — otherwise "we use 2.1 GB" is a fact with no verdict attached.

The second consequence of the cliff is that peak matters more than average. A game that idles at 1.2 GB and touches 1.9 GB for 400 ms during a level transition, while both the outgoing and incoming levels are resident, is a 1.9 GB game. Every allocation strategy in this lesson is ultimately aimed at that transient peak: keeping two things from being resident at once, or making the transient thing come out of memory you already own.

2Four heaps, four different failure modes

"Memory usage" is not one number, and the single most common mistake in a student memory report is quoting one. A game process has several allocators with different owners, different lifetimes, and different tools. If you do not say which one grew, you have not diagnosed anything.

Managed / GC heap
C# objects in Unity, UObjects in Unreal

Grows in pages; in Unity's Boehm collector it historically does not return pages to the OS, so the high-water mark is your footprint for the rest of the session. Fails as: rising baseline, GC pauses, eventual OOM on constrained platforms.

Native heap
Engine, plugins, physics, audio, C++ containers

Real malloc/new. Real leaks are possible here — memory with no reference at all. Fails as: steady linear growth invisible to a managed profiler, or fragmentation of the address space.

Graphics / VRAM
Textures, meshes, render targets, shaders

Usually the biggest number in the report and the one students forget to attribute. On unified-memory devices (consoles, mobile) it comes out of the same pool as everything else. Fails as: streaming stalls, texture pop-in, driver-level allocation failure.

Streaming & reserved pools
Audio banks, level streaming, IO buffers

Memory you deliberately reserved and now must live inside. Fails as: an audio bank that cannot load, a streaming level that never finishes, a texture that stays at the lowest mip forever because the streaming budget is exhausted.

Attribute before you optimize. A report that says "memory went from 1.9 GB to 1.6 GB" is worth much less than one that says "managed heap 210 MB → 118 MB, texture memory unchanged at 840 MB, native down 40 MB after we stopped double-buffering the navmesh." The second version tells your reader which of the four failure modes you actually addressed, and it is the form your assignment's before/after section should take.

3In a GC language, a "leak" is a retention bug

In C++ a leak is unambiguous: you called new, you never called delete, and the allocation has no reference anywhere in the program. The memory is unreachable and unfreeable. Valgrind will point at the exact call stack, because unreachability is a property a tool can compute.

C# and Unreal's UObject system do not leak that way, and this trips up nearly every student the first time. A garbage collector frees everything unreachable, correctly, every time. So if memory is climbing in managed-land, the collector is not broken — something is still pointing at the objects, and that something is code you wrote. The bug is not "we forgot to free." It is "we forgot to forget." That reframing changes how you hunt: you stop looking for missing cleanup calls and start looking for surviving references, which is exactly what a memory profiler's reference path or retainer chain view shows you.

Static collections

A static List<T> is a GC root that lives as long as the domain. Anything you add and never remove is immortal, along with everything it transitively references.

Events never unsubscribed

Subscribing makes the publisher hold a reference to the subscriber. A long-lived event source therefore keeps every short-lived listener alive. The arrow points the opposite way from how students imagine it.

Closures capturing this

A lambda that touches an instance field compiles to a class holding a reference to the whole instance. Store that lambda in a timer, a callback table, or an async continuation and you have retained the object graph behind it.

Orphaned persistent objects

DontDestroyOnLoad in Unity, AddToRoot() in Unreal. Both say "never collect this." Both are correct once and catastrophic on the second scene load, because now you have two of them, then three.

Why this is the highest-value hour in the topic

Do the arithmetic on the second failure mode. A wave spawner that subscribes to a game-instance event and never unsubscribes retains itself, its enemy prefab references, and its pooled particle systems — call it 1.4 MB of managed objects plus the textures they keep alive. That is nothing. Now load the level 40 times during an eight-hour soak test, which is roughly what a QA pass looks like, and you are holding 56 MB of dead spawners plus their texture references. On a 1.5 GB mobile budget that single missing -= is 4% of the entire game. It costs one line to fix and it is invisible in every test shorter than ten minutes.

4Fragmentation: why 300 MB free can fail a 40 MB request

Here is the failure that convinces students memory is its own discipline. The profiler says you have 312 MB free. The game asks for a 40 MB contiguous buffer — a streamed texture atlas, a decompression scratch buffer, an audio bank — and the allocation fails. Nothing leaked. Nothing is over budget. The arithmetic is fine and the request still cannot be served.

The reason is that an allocator hands out contiguous ranges of address space, not abstract megabytes. Free memory accumulates as a set of holes between live allocations, and the size that matters is not the sum of the holes but the largest single one. Allocate a mix of block sizes with a mix of lifetimes, free them in an order unrelated to the order you allocated them, and the free space shatters into a hundred fragments none of which is big enough for a large request. This is external fragmentation, and it is a property of the pattern of allocation and release, not of how much memory you use.

Why consoles and phones get hit and your PC does not

A desktop process has a 64-bit virtual address space and an OS that maps physical pages behind it on demand. Holes in the virtual address space are enormous and cheap, so external fragmentation is mostly invisible to you. A console partition, a fixed-size reserved pool, or a mobile process under a jetsam limit has none of that slack: you are allocating out of a bounded region, and the holes are the only free memory there is. Hizon et al. (2002) were writing about exactly this constraint on fixed-hardware consoles, and their conclusion has aged well — on a fixed budget you do not manage memory by using less of it, you manage it by controlling the shape of what you allocate. That is why shipped console engines route almost everything through pools and arenas rather than a general-purpose heap.

Play with the sandbox below before reading further. It is a real free-list simulator: a 128 MB asset region held as a block list, first-fit or best-fit placement, and adjacent-free coalescing on every release. It starts already booted, because a real game's heap is never pristine — the boot sequence allocated, peaked near 95 MB, and left long-lived objects scattered behind it. Four things to notice. First, the heap is only about a quarter occupied when the request fails. Fragmentation is not a symptom of being full; it is a symptom of the pattern. Second, the failure survives every cycle from about the second one onward, because the long-lived small objects scattered during the boot peak are immovable pins — and the free space between two pins can never exceed the distance between them, no matter how much total memory you free.

Third, switch the strategy to best-fit and run the same cycles. It is not a fix and it is not uniformly worse: best-fit consumes the smallest adequate hole, which preserves large runs longer, so the request often still succeeds — while the number of free holes and the population of unusable sub-2 MB slivers grows steadily. Push the transient slider up and keep churning and it fails too. That is the honest summary of the placement-policy literature: policies trade the shape of the failure, none of them removes it, and this is why the industry answer is not "choose a smarter heap."

Fourth, switch to the segregated strategy and keep churning. The 40 MB request stops failing, permanently. Not because the allocator got clever but because two structural decisions were made in advance: short-lived small objects can only land in the slot pool, so they can never pin the middle of a large region, and the region large transient buffers come from was reserved at startup, so nothing else can take it. A fixed-size pool converts unbounded external fragmentation into bounded, predictable internal fragmentation — the "wasted in slots" readout, which runs around 10 MB here and is the price you agree to pay up front. It also converts a failure you cannot predict into one you can: undersize the pool and it refuses an allocation on a schedule you can compute, rather than at 2 a.m. on a test kit. Trading an unpredictable failure for a predictable overhead is the whole argument for pooling, and it is the sentence to put in your assignment.

What this means in each engine

You do not control the managed heap's placement policy, so your lever is the allocation pattern itself. Pool GameObjects rather than Instantiate/Destroy per spawn: a pool is a fixed-size allocator wearing a gameplay costume, and it removes the churn that shreds both the managed heap and the native side. Pre-size collections with the capacity constructor so they stop doubling their backing arrays mid-level. For large native buffers, allocate once at load and reuse — NativeArray<T> with Allocator.Persistent allocated during a loading screen fragments nothing; the same array allocated per wave does. Addressables let you control when large blocks come and go, which is the same lever: group assets by lifetime so that things released together were allocated together.

Watch for the specific Unity trap: the managed heap expands to its high-water mark and does not hand pages back to the OS under the Boehm collector, so a single transient spike permanently raises your floor. That is not fragmentation, but it has the same shape on a graph and students misdiagnose it constantly. Distinguish them with the Memory Profiler: fragmentation shows as a heap section with live objects scattered across many pages; a high-water mark shows as large contiguous empty regions inside a reserved heap.

Unreal gives you the allocator directly. FMemory routes to a pluggable allocator (binned2/binned3 on most platforms), which is itself a segregated free-list design: small allocations are served from size-class pools exactly like the sandbox's pool mode, and large ones go to the OS. That is why most Unreal fragmentation problems show up in the large-block path, and why the fix is usually about lifetime grouping rather than allocator tuning. Use TArray::Reserve before a known-size fill so the array does not walk through five intermediate capacities, leaving four holes behind. Prefer TInlineAllocator for small hot arrays so they never touch the heap at all.

For the game-object equivalent, object pooling is built in as actor pooling patterns and, for UObjects, cluster GC keeps related objects together so they are collected as a unit. When you need hard evidence, stat memory and memreport -full give you the per-category picture, and Low Level Memory Tracker (LLM) attributes allocations to subsystems — the only way to say "the growth is in audio, not in rendering" without guessing.

Your console build fails a 40 MB streaming allocation with 300 MB free. Which change is most likely to actually fix it?

Why C: A block you own from startup cannot be denied later, and pools stop short-lived allocations from landing inside the region large requests need. You have removed the failure mode rather than making it less likely — and "less likely" is a poor property for a bug that only appears after two hours of play on the test kit.
Why A is tempting
Best-fit sounds like it wastes less, and in the sandbox it genuinely does delay the failure — which is exactly what makes it a trap. It buys time while accumulating unusable slivers, so the bug reappears later, on a different level, and now with a "we already fixed that" note in the ticket. No placement policy solves fragmentation against arbitrary lifetimes.
Why B is tempting
Using less memory is good and you should do it, but the request did not fail for lack of total free memory — there was 300 MB. Freeing another 100 MB in small scattered pieces can leave the largest contiguous run exactly where it was. Fixing the wrong axis is the classic fragmentation mistake.

5Allocation rate, not allocation count, is the metric

Once you accept that the collector always frees what is unreachable, the interesting question stops being "how much garbage did I make" and becomes "how fast am I making it." A tracing collector's cost is dominated by the mark phase, which walks the live object graph. That cost is proportional to how much is alive, not to how much is garbage. Your allocation rate sets how often you pay it.

So the frame-time damage from garbage collection is the product of two numbers you control separately: rate (KB allocated per frame) determines collection frequency, and live set (MB of reachable objects) determines the length of each pause. A game with a small heap can allocate carelessly and get short, frequent, tolerable pauses. A game with a 200 MB live heap that allocates 150 KB per frame gets a 60–80 ms stall every few seconds, which is four or five dropped frames in a row — the exact pattern players describe as "it stutters."

Why your average FPS will not show this and your review will

Do the arithmetic before you run the simulator. Take a 20-second capture — 1,200 frames at a 14 ms baseline — and add nine collections of 64 ms each. Total time rises by 576 ms over 16.8 s, so average frame time goes from 14.0 to about 14.5 ms: 71 fps down to 69 fps. Nobody files that. Meanwhile the twelve worst frames in the capture are nine 78 ms monsters and three ordinary ones, so the 1% low is about 62 ms — roughly 16 fps, down from about 68. This is the Topic 4 lesson arriving in memory form: the average is nearly unchanged and the game feels broken. Report percentiles or you will optimize the wrong thing.

Unreal's version of the same trade

Unreal's UObject collector is generational only in the loose sense but it is clustered: related objects (an actor and its components, an asset and its sub-objects) are collected as a unit, which shrinks the graph the reachability pass has to walk. The tuning knobs are real and measurable — gc.TimeBetweenPurgingPendingKillObjects, incremental purge budgets, and cluster settings — and the diagnostic is stat gc plus gc.CollectGarbageEveryFrame 1 to force the worst case while you profile. The advice mirrors C#: the number of UObjects is the cost driver, so a system that spawns 10,000 tiny UObjects will pay on every collection, and the fix is to make them not be UObjects — plain structs in a TArray, which is also the data-oriented answer Wingqvist, Wickstrom & Memeti (2022) measure.

A build allocates 40 KB/frame with a 90 MB live heap. Your fix candidates: (i) cut allocation to 8 KB/frame, or (ii) cut the live heap to 45 MB by unloading unused assets. Which has the bigger effect on 1% low fps, and why?

Why A: Both help, but they act on different terms. Halving the live set halves each pause (roughly 32 ms to 16 ms here) — still a dropped frame. Cutting the rate by 5× means one fifth as many collections, so the number of ruined frames drops by 80%. Since 1% low is a count-of-bad-frames statistic, frequency beats magnitude. Set the simulator to 40 KB/90 MB and try each change to see it.
Why B is tempting
It is the intuitive one, and it is genuinely correct about the mechanism: mark cost really does scale with live objects. But a 16 ms pause still blows a 16.6 ms budget, so you have converted a catastrophic frame into a merely bad one at the same frequency. Halving pain you take just as often is a weaker result than taking it a fifth as often.
Why C is tempting
Shader hitches and streaming stalls absolutely do dominate 1% lows in some titles — that was Topic 4's frame-time reader. But the question hands you a measured allocation rate and heap size, which is precisely the case where GC is the identified cause. Dismissing the measurement you have in favour of a general truth is how investigations stall.

6Snapshot diffing: the one technique to take away from this topic

If you remember one method from these four sessions, make it this one. Almost every memory investigation you will ever run reduces to the same three-step protocol, and it works identically in Unity, in Unreal, in Visual Studio's diagnostic tools, and in Xcode Instruments:

  1. Snapshot A. Get the game into a known steady state — a specific level, a specific menu, nothing streaming. Force a collection. Take the snapshot.
  2. Act. Do the suspect thing N times, where N is large enough that a per-iteration leak is unmistakable: open and close the inventory twenty times, load and unload the sub-level three times, spawn and kill two hundred enemies.
  3. Snapshot B, back at the same state. Return the game to exactly the state of snapshot A. Force a collection again. Take the second snapshot and diff it.

Everything the diff shows is, by construction, something the action created and the return did not release. You are not asking "what is using memory," a question whose answer is thousands of rows of nothing in particular. You are asking "what survived a round trip that should have been net-zero," a question with a short answer and a suspect list. That framing is why the technique outperforms staring at a total.

The two steps students skip, and what it costs them

Returning to the same state is what makes the diff meaningful. Snapshot A in the hub and snapshot B in the dungeon differ by an entire level, so the diff is noise and you learn nothing. Forcing a collection before each snapshot is what removes false positives: uncollected garbage is still resident, so without a collect you will see hundreds of objects "leaking" that the next GC would have taken. In Unity that is GC.Collect() followed by Resources.UnloadUnusedAssets(); in Unreal it is obj gc (or GEngine->ForceGarbageCollection(true)). Doing it for real

Install the Memory Profiler package — the built-in Profiler's memory module gives you totals, and totals do not diagnose. Attach to a development player on the target device, not the editor: editor snapshots include editor-only allocations, asset import caches, and a domain full of objects that never exist in a build, which is why editor-only memory investigations produce conclusions that do not survive contact with the phone.

The workflow: capture snapshot A, act, capture snapshot B, then open the two together and use the diff view. Sort by the count delta, not the size delta — a leak of many small objects is a stronger signal than one big allocation, which is usually a legitimate asset. When a suspicious type appears, select an instance and read its reference path back to a root. That chain is your answer: it will terminate in a static field, an event's invocation list, a DontDestroyOnLoad object, or a ScriptableObject asset, which maps directly onto the four mechanisms in section 3.

MemoryProbe.cs — make the protocol repeatable
// Bind to a debug key. A protocol you can run identically in build N+1
// is worth more than a cleverer one you run once.
public static void Settle() {
    GC.Collect();                                // drop unreachable managed objects
    GC.WaitForPendingFinalizers();
    GC.Collect();                                // finalizers can resurrect; collect twice
    Resources.UnloadUnusedAssets();               // native side: textures, meshes, audio
    Debug.Log($"mono={Profiler.GetMonoUsedSizeLong()} " +
              $"total={Profiler.GetTotalAllocatedMemoryLong()}");
}

Log those two numbers at fixed checkpoints — main menu, level load complete, level unload complete — in every automated run. A CSV of checkpoint memory across builds turns "it feels like memory is growing" into a regression you can bisect, which is the same discipline Topic 3 applied to tests.

Unreal's equivalents are console commands, which makes them trivially scriptable into an automation run. memreport -full writes a report with per-category totals, the largest objects, and texture/audio breakdowns; run it at your two checkpoints and diff the files with any text diff tool. obj list -class=Texture2D and obj list class=StaticMesh give per-class counts and sizes; obj refs name=SomeAsset prints the reference chain that keeps an object alive — the direct analogue of Unity's reference path, and the fastest route from "this should have been unloaded" to "this is who is holding it."

Low Level Memory Tracker is the attribution tool: launch with -LLM and stat LLM (or the LLM track in Unreal Insights) breaks the process total into engine-defined tags — Textures, Meshes, Audio, Physics, UObject, RHI misc. Without it you can see that native memory grew; with it you can say which subsystem grew, which is the difference between a finding and a guess. For the true C++ leaks that no reachability scan will catch, use Visual Studio's Diagnostic Tools snapshots on Windows or Valgrind/Massif on Linux builds.

Console protocol — run these in order, in a packaged development build
// A: settle and capture
obj gc
memreport -full
obj list class=Texture2D

// Act: open/close, load/unload, spawn/destroy — N times

// B: settle and capture again, same state as A
obj gc
memreport -full
obj list class=Texture2D

// Then: who is holding the thing that should be gone?
obj refs name=T_Boss_Albedo

You take snapshot A in the hub, play the dungeon for five minutes, return to the hub, and take snapshot B without forcing a collection. The diff shows 4,300 new System.String objects. What have you actually learned?

Why B: A snapshot captures what is resident, not what is reachable. Unreferenced garbage sits in the heap until the next collection, so any diff taken without settling first is measuring "garbage not yet collected" mixed with real retention, with no way to separate them. Force the collect, re-take it, and the 4,300 usually becomes 0 or becomes a real, much smaller number worth chasing.
Why A is tempting
It is the right shape of conclusion from the wrong measurement. Strings genuinely are a common retention target — caches keyed by name are a classic — but you have not yet done the one step that would make the evidence admissible.
Why C is tempting
It smuggles in two errors: a count is not a size (4,300 short strings might be 200 KB), and churn is not consumption. Even if the strings are real garbage, the fix belongs in the allocation-rate conversation from section 5, not in a leak report. Fix what you measured, and measure what you are about to claim.

7Cross-platform prevention, and the trade you have to defend

Prevention beats detection here more than anywhere else in the course, because memory defects are discovered on the platform you test last. The strategies below are ordered by how much they buy you per hour of work, and all of them are things you do before the bug exists.

The cross-platform part deserves its own warning, because the same build behaves differently for reasons that are not in your code. On a unified-memory device your textures come out of the same pool as your game logic, so a texture budget decision is a gameplay budget decision. Mobile operating systems complicate the accounting further: what the OS reports for your process includes shared pages, file-backed pages, and cached data, and it may reclaim some of that under pressure without telling you. Chen et al. (2018) study exactly this layer — the interaction between an app's memory and the system page cache on mobile — and the practical takeaway for you is narrow but important: the number the OS shows and the number your profiler shows are measuring different things, and the one that gets you killed is the OS's. Always report both, and always name which one you used.

Why the balance conversation goes badly, and how to win it

Your objective list ends with "balance memory optimization against gameplay and visual quality," which in practice means a meeting where you propose halving a texture budget and an artist says no. Two things make that meeting go well. First, bring the cliff: "at 1.9 GB peak we are 180 MB over the jetsam limit on the oldest supported iPhone, which is a crash on level transition, which is a cert failure — not a quality trade, a ship/no-ship." Second, bring an ordered menu of options with measured costs, not a single demand: a 2048→1024 cap on hero textures saves 128 MB and is visible at close range; dropping one shadow cascade saves 24 MB and is visible at distance; streaming the third audio bank saves 60 MB and costs 200 ms on a rare transition. Artists and designers make excellent decisions when handed a priced menu and terrible ones when handed an ultimatum. That is a professional skill, not a technical one, and it is what the assignment's "prevention strategies" section is really asking you to demonstrate.

One more source of cross-platform surprise worth naming for anyone doing a networked project. Deng & Lau (2012) look at load balancing in distributed virtual environments — how you redistribute load across servers and how the delay in doing so affects the result. The memory parallel is exact and often overlooked: server-side, a region's resident state is a memory cost per machine, and migrating players to rebalance CPU also migrates their resident state. If your project has a dedicated server, its memory budget per instance is as real as the client's, and it is measured under peak concurrency rather than in your two-player test.

9The reading, and what to take from each

  • Hizon, Fernandez & others (2002), "Play by Play: Effective Memory Management." Old hardware, current argument. Read it for the mindset that a fixed budget makes memory a design constraint handled by controlling allocation shape — pools, arenas, load-time reservation — rather than a runtime problem solved by cleverness. Everything in section 4 descends from this position.
  • Chen et al. (2018), "Enabling Union Page Cache…" Read it for the systems layer underneath your profiler: what the OS counts as your memory, what it shares, and what it can reclaim. The takeaway to carry into your report is that process-level and engine-level numbers disagree for legitimate reasons, and you must say which you measured.
  • Wingqvist, Wickstrom & Memeti (2022), "Evaluating the Performance of Object-Oriented and Data-Oriented Design with Multi-Threading in Game Development." The memory-layout argument with measurements attached. Data-oriented design is usually sold as a cache-locality win; note that it is also an allocation-count win, because a thousand entities in one array is one allocation and one GC edge rather than a thousand of each.
  • Deng & Lau (2012), "On Delay Adjustment for Dynamic Load Balancing in Distributed Virtual Environments." Server-side resource management under change. Relevant if your project is networked: resident state is a per-instance memory cost, and rebalancing moves it.

Bring to the assignment

Memory Optimization · 100 points · due Nov 22 · document at least two memory issues found by profiling, fix each, measure before and after, and develop cross-platform prevention strategies. Slides, a 5–7 minute video, or a report.

What a strong submission contains, in the order a grader looks for it:

  • A stated budget before any measurement. Target platform, total memory budget in MB, and a category breakdown. Without it your numbers have no verdict. One table, five lines.
  • Two issues of different kinds. Two retention leaks is a weaker submission than one retention leak plus one of: allocation-rate churn causing GC spikes, a fragmentation or large-allocation failure, an unnecessary texture/audio residency, or a native leak. Section 2's four heaps is the menu — pick from two different rows.
  • Evidence that names the mechanism. For a retention bug, the reference path or obj refs chain terminating in the root, plus the line of code that created it. "It was a leak" is not a diagnosis; "a static event's invocation list held 37 dead spawners" is.
  • The three-snapshot protocol, stated and repeated. Snapshot A, N iterations, snapshot B at the same state, forced collection before both, N written down. Run it identically before and after the fix — the same protocol on both sides is what makes the comparison admissible.
  • Before/after numbers with units and percentiles. Managed heap MB, native MB, texture MB, per-iteration retained bytes, and — if the issue was GC churn — average frame time and 1% low, because the average will not move and you need to explain why that is the point.
  • Prevention, written as rules, not intentions. Take section 7's table and fill in your project's version: the budget document, the CI checkpoint, the pooling rule, the teardown checklist line. A rule someone else could follow beats a paragraph about being careful.
  • The cross-platform delta. State how the same fix behaves on a second target — desktop versus mobile, or editor versus device. If you can only test one, say what you predict and why, in terms of unified memory, the OS limit, and the texture format difference.
  • One honest trade. Something you chose not to optimize because the visual or gameplay cost was too high, with the number you would have saved. Graders and studios both read that as the sign of an engineer rather than a tuner.
