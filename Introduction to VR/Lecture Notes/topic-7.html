1. What “cohesive” actually means

Integration is where student projects most often fall apart, and rarely because any single system is broken. Each system was built and tested alone, against its own assumptions: the forest team assumed the player starts at (0, 0, 0); the UI team assumed a 1.6 m eye height; the audio team put an AudioListener on its test camera. Put them together and you have two listeners, a player spawning inside a rock, and a menu at knee height in the seated ruins scene.

Cohesion is the opposite of that experience. It is not polish; it is consistency along six specific axes. Audit your game against each one before you touch a line of loading code:

Integration

Combining independently built systems into one product and resolving the conflicts that only appear when they meet. Integration is work — budget days for it, not an evening.

Why it matters: every milestone so far was tested in isolation. Integration is the first time your game is tested as a game.

Cohesion

Consistency of scale, input, UI language, audio mix, art direction, and rules across all scenes, so the player experiences one deliberate world rather than three team members' habits.

Why it matters: presence survives a low-poly tree; it does not survive a grab button that changes between rooms.

Scene architecture

The deliberate plan for which scenes exist, what each owns, and how they load. The alternative — one giant scene, or three scenes that each contain their own copy of the player — is the source of most integration bugs.

Persistent (bootstrap) scene

A small scene that is loaded first and never unloaded. It owns the things that must exist exactly once: the XR Origin, the managers, the audio mixer and listener, the fade quad, and the loader itself. Realm scenes contain only their world.

Why it matters: “exactly once” is the cure for duplicate XR Origins and multiple AudioListeners.

Additive loading

Loading a scene on top of what is already loaded (LoadSceneMode.Additive) instead of replacing it (Single). The bootstrap scene stays; the forest is added; later the forest is unloaded and the mountain pass is added.

Asynchronous loading

SceneManager.LoadSceneAsync reads and deserializes the scene over several frames on a background thread, so the frame rate stays up while the player looks at a fade. Synchronous LoadScene freezes the headset for the whole load — on Quest that is a black, frozen world for one to three seconds.

Scene activation

The moment loaded objects are actually instantiated and their Awake/Start run. Unity's AsyncOperation.progress stops at 0.9 while allowSceneActivation is false; setting it true triggers activation, which always costs one heavy frame. Hide that frame behind the fade.

Why it matters: the most common student loader bug is leaving allowSceneActivation false forever. The load “hangs” at 90%.

Spawn anchor

An empty GameObject in each realm scene (named, say, Spawn_FromForest) whose position and forward define where the XR Origin is placed on arrival. One per entrance, at floor level, facing the first thing the player should see.

2. The load sequence, frame by frame

A good transition is six steps: fade to black, start the async load with activation held back, wait until progress reaches 0.9, unload the previous realm, allow activation (the expensive frame), move the rig to the spawn anchor, then fade back in. The widget below simulates that sequence. Scene size and storage speed set the load time; the activation cost is the Awake/Start frame; the two toggles reproduce the two most common mistakes.

Scene-transition timelineAsync load, activation, and fades on a timeline. Turn on the mistakes to see what the player experiences.

Two ideas to take from the timeline. First, time in black is the number the player feels; anything under about a second reads as a deliberate transition, and beyond two seconds people take the headset off to check it is still working. Second, the activation frame cannot be made asynchronous — it runs every Awake in the scene on the main thread — so the only cure for a 400 ms activation is a lighter scene: fewer objects with scripts, no heavy work in Start, prefabs that initialize lazily.

using System.Collections;
using UnityEngine;
using UnityEngine.SceneManagement;

/// Lives in the Bootstrap scene. Swaps realm scenes additively, hides the
/// activation frame behind a fade, and places the rig on a named spawn anchor.
public class RealmLoader : MonoBehaviour
{
    [SerializeField] private ScreenFader fader;      // black quad in front of the camera, alpha 0..1
    [SerializeField] private Transform xrOrigin;     // the RIG ROOT — never the camera
    [SerializeField] private float fadeSeconds = 0.4f;
    private string current;                          // realm scene currently loaded (null at boot)

    public void Go(string sceneName, string anchorName) => StartCoroutine(Transition(sceneName, anchorName));

    private IEnumerator Transition(string sceneName, string anchorName)
    {
        yield return fader.FadeTo(1f, fadeSeconds);                       // 1. to black

        AsyncOperation load = SceneManager.LoadSceneAsync(sceneName, LoadSceneMode.Additive);
        load.allowSceneActivation = false;                                 // 2. stream in, but do not activate yet
        while (load.progress < 0.9f) yield return null;                    //    progress parks at 0.9 until we allow it

        if (!string.IsNullOrEmpty(current))                                // 3. free the old realm FIRST (memory peak)
            yield return SceneManager.UnloadSceneAsync(current);

        load.allowSceneActivation = true;                                  // 4. the one expensive frame: every Awake/Start
        yield return load;
        current = sceneName;
        SceneManager.SetActiveScene(SceneManager.GetSceneByName(sceneName)); // lighting/skybox follow the ACTIVE scene

        GameObject anchor = GameObject.Find(anchorName);                   // 5. place the player at floor level, facing the view
        if (anchor != null)
            xrOrigin.SetPositionAndRotation(anchor.transform.position, anchor.transform.rotation);
        yield return null;                                                 //    one frame for tracking to settle

        yield return fader.FadeTo(0f, fadeSeconds);                       // 6. reveal
    }
}
Where the XR Origin lives

Exactly one XR Origin, in the bootstrap scene, marked so it is never duplicated. Realm scenes must contain no camera and no AudioListener. If a teammate needs a camera to work on a realm scene alone, they keep a disabled “editor-only camera” prefab that a one-line script destroys in Play mode. Two listeners produce the warning “There are 2 audio listeners in the scene” and silence half your spatial audio; two rigs produce a player who teleports into a copy of themselves.

3. Game state and progression

Your game has state that outlives any one scene: which artifact pieces are collected, which puzzles are solved, which realm the player is in, their comfort settings. Game state needs a home that is not inside a realm scene, because realm scenes get unloaded. Two patterns are standard; most teams use both.

State machine

A model of the game as a finite set of states (Title, Forest, MountainPass, Ruins, Ending, Paused) and the transitions allowed between them, each triggered by an event and optionally guarded by a condition (“enter the mountain portal” requires the forest piece). Making the machine explicit turns “why can I open the pause menu during the ending?” from a mystery into a missing arrow.

Singleton

A class guaranteed to have one instance, reachable globally (GameManager.Instance). Convenient, and fine for genuinely unique services (save system, audio mixer control). Dangerous when everything reaches into it — it becomes a hidden dependency of every script, and tests and merges get harder.

Why it matters: one GameManager that holds state and a loader is reasonable. Fifteen singletons that call each other in Awake is an initialization-order lottery.

ScriptableObject event channel

A ScriptableObject asset that exists only to be raised and listened to. The rune puzzle raises OnPieceCollected; the inventory, the HUD, the audio manager, and the save system each listen. None of them reference each other — they all reference the asset. Scenes can be tested alone because the asset exists whether or not the listeners do.

Why it matters: event channels are how three teammates' systems talk without importing each other's scripts.

Save / load

Serializing the game state to storage and restoring it. On Quest, Application.persistentDataPath is your writable folder; JsonUtility turns a [Serializable] class into readable JSON. PlayerPrefs is fine for a handful of settings (comfort preset, volume) but awkward for structured progress.

Persistence

The general property that something survives beyond its natural lifetime: across scene loads (an object kept alive), across app restarts (a save file), across devices (a cloud save — out of scope here). Decide per piece of state which kind of persistence it needs.

DontDestroyOnLoad

Object.DontDestroyOnLoad(gameObject) moves an object into a special scene that survives Single loads. With a bootstrap scene and additive loading you rarely need it — the bootstrap scene already persists — but it is the classic way to keep a music AudioSource or telemetry logger alive if you use single-scene loads anywhere.

using UnityEngine;
using UnityEngine.Events;

/// An asset that carries an event. Create one via the menu, drag it into the
/// raiser (the puzzle) and into every listener (inventory, HUD, audio, save).
[CreateAssetMenu(menuName = "Realm/Events/Piece Collected")]
public class PieceEventChannel : ScriptableObject
{
    public event UnityAction<string> OnRaised;          // payload: the artifact piece id
    public void Raise(string pieceId) => OnRaised?.Invoke(pieceId);
}

/// A listener. Note that it never references the puzzle, the HUD, or the GameManager.
public class InventoryListener : MonoBehaviour
{
    [SerializeField] private PieceEventChannel pieceCollected;
    [SerializeField] private Progress progress;                // plain data object, see SaveSystem

    private void OnEnable()  => pieceCollected.OnRaised += Add;   // subscribe when the scene/rig is live
    private void OnDisable() => pieceCollected.OnRaised -= Add;   // ALWAYS unsubscribe: the asset outlives the scene

    private void Add(string pieceId)
    {
        if (progress.pieces.Contains(pieceId)) return;             // idempotent: raising twice must not duplicate
        progress.pieces.Add(pieceId);
        SaveSystem.Save(progress);                                 // persist immediately; Quest apps get killed without warning
    }
}
using System.Collections.Generic;
using System.IO;
using UnityEngine;

/// Everything that must survive a restart, as plain serializable fields.
[System.Serializable]
public class Progress
{
    public string realm = "Forest";                 // last realm entered
    public string anchor = "Spawn_Start";           // where to place the rig on resume
    public List<string> pieces = new List<string>(); // artifact pieces collected
    public List<string> solved = new List<string>(); // puzzle ids
    public bool teleportOnly = true;                // comfort preset chosen in onboarding
    public float playSeconds;
}

public static class SaveSystem
{
    // persistentDataPath is the only folder guaranteed writable on Quest (Android).
    private static string FilePath => Path.Combine(Application.persistentDataPath, "progress.json");

    public static void Save(Progress p)
    {
        File.WriteAllText(FilePath, JsonUtility.ToJson(p, prettyPrint: true));
    }

    public static Progress Load()
    {
        if (!File.Exists(FilePath)) return new Progress();        // first run: defaults
        try { return JsonUtility.FromJson<Progress>(File.ReadAllText(FilePath)); }
        catch { return new Progress(); }                           // corrupt file beats a crash on launch
    }
}

Namespaces and folders

Wrap your scripts in namespace Realm.Audio, Realm.Puzzles, and mirror that in Assets/_Project/Scripts/Audio. Two teammates both writing a Timer class stop colliding, and the folder tells a reader which system owns a file.

Assembly definition (.asmdef)

An asset that compiles a folder of scripts into its own assembly. Benefits: faster recompiles (only the changed assembly rebuilds) and enforced dependencies — Realm.Puzzles cannot reference Realm.UI unless you add the reference. A mention is enough for this course; if your compile times pass ten seconds, try one per system.

Merge conflict

What Git reports when two people changed the same lines of the same file. Text files (C#) merge well. Unity scene and prefab files are YAML text but merge badly — a resolved conflict in a .unity file frequently produces a scene that will not open.

Why it matters: the rule from Week 2 still stands: one person edits a scene at a time. Announce it in your team chat before you open it.

Prefabs as merge units

Anything two people might edit belongs in a prefab, not directly in the scene. The scene then holds only prefab instances; each prefab is a separate file with one owner. The rune puzzle, the guide NPC, the HUD, each spawn anchor group — all prefabs.

Scene ownership

A written list: Forest — Ana; MountainPass — Ben; Ruins — Chloe; Bootstrap — whoever is integrating this week. Anyone else who needs a change in a scene asks the owner or edits a prefab. It feels bureaucratic; it prevents the Sunday-night “the ruins scene is gone” message.

Git LFS

Large File Storage: a Git extension that stores binaries (textures, audio, FBX) outside the main history and keeps the repository fast. Track *.png *.fbx *.wav *.ogg and similar via .gitattributes. Without it, a 300 MB texture folder makes every clone a lunch break.

Memory budget

The amount of RAM your app may use before the OS kills it or the compositor stutters. The Quest 3 has 8 GB in total; a safe working target for a student project is about 2 GB, and textures are almost always the largest slice.

Why it matters: a memory crash on the third scene load is the most common “it worked yesterday” report in Week 14.

Garbage collection (GC)

C# allocates objects on a managed heap and periodically collects the ones no longer referenced. On Unity's default collector the collection stops the whole main thread while it scans the heap — a few milliseconds for a small heap, tens for a large one.

GC spike

A single long frame caused by a collection: 13.9 ms of normal work plus 20–40 ms of GC equals two or three dropped frames and a visible hitch. Spikes are periodic, so players report “it stutters every few seconds.” Cause: allocating garbage every frame (string concatenation in Update, new lists, LINQ, Instantiate/Destroy churn).

Object pooling

Creating a fixed set of objects up front and reusing them (enable/disable, reposition) instead of instantiating and destroying. Removes both the allocation and the activation cost from the hot path. Unity ships UnityEngine.Pool.ObjectPool<T>; use it for sparkles, projectiles, footstep sounds, floating damage text.

Addressables

Unity's package for loading assets by address (a string key) asynchronously, from inside or outside the build, with reference counting so unused assets can be unloaded. It is how larger projects keep memory flat while streaming realms. For this course a mention: if a realm's textures alone exceed the budget, addressables are the next tool to learn.

Regression

Something that used to work and no longer does, usually because of a change elsewhere. Integration is a regression factory: the forest ran at 72 fps alone, and now runs at 58 because the bootstrap scene added a real-time directional light on top of the forest's baked one.

Where the memory goes

Memory is a sum of a few large terms, and the arithmetic is simple enough to do in your head once you know the per-item costs. A texture costs width × height × bytes per pixel × 1.33 (the 1.33 is the mipmap chain); ASTC 6×6 compression stores about 0.44 bytes per pixel against 4 for uncompressed RGBA. PCM audio costs about 11.5 MB per stereo minute at 48 kHz; Vorbis kept compressed in memory costs about 1 MB per minute. Meshes cost roughly 32–48 bytes per vertex. 2. The integration regression checklist

Every one of these has appeared in a student project in the week after integration. Check them in this order; the first four take five minutes and fix half of all reports.

  • Multiple AudioListeners. Search the Hierarchy of the running game for t:AudioListener. Exactly one, on the XR Origin's camera.
  • Duplicate XR Origins. Search t:XROrigin. Exactly one. A duplicate usually arrived inside a realm scene that was “tested standalone.”
  • Real-time lights by mistake. Every Light in realm scenes should be Baked or Mixed; one real-time directional light with shadows can cost 3–4 ms on Quest.
  • Missing Static flags. Rocks, walls, ruins: Static checkbox on, so static batching and light baking apply. Only things that move should be dynamic.
  • GC churn in Update. String concatenation for the HUD ("Pieces: " + n allocates every frame), GetComponent in Update, Instantiate/Destroy for sparkles. Profile with the GC Alloc column; the target in steady state is 0 B per frame.
  • Post-processing stacked twice. A Volume in the bootstrap scene and another in the realm both active. Keep one global volume in bootstrap; realms add local volumes with only what differs.
  • Quality settings reset. Confirm the Android quality level uses MSAA 4×, no real-time shadows on distant cascades, and the URP asset you tuned in Topic 3 — a merge can silently swap it.
  • Scene not in the build list. LoadSceneAsync of a scene missing from Build Profiles logs an error and returns null; the coroutine then throws. Check the list after every merge.
using System.Collections;
using UnityEngine;
using UnityEngine.Pool;

/// Reuses a fixed set of particle bursts (collect a piece, solve a rune) so the
/// hot path never calls Instantiate/Destroy and never allocates garbage.
public class SparklePool : MonoBehaviour
{
    [SerializeField] private ParticleSystem prefab;
    [SerializeField] private int prewarm = 8;
    [SerializeField] private int maxSize = 32;
    private ObjectPool<ParticleSystem> pool;

    private void Awake()
    {
        pool = new ObjectPool<ParticleSystem>(
            createFunc:      () => Instantiate(prefab, transform),
            actionOnGet:     p  => p.gameObject.SetActive(true),
            actionOnRelease: p  => p.gameObject.SetActive(false),
            actionOnDestroy: p  => Destroy(p.gameObject),      // only when the pool shrinks past maxSize
            defaultCapacity: prewarm, maxSize: maxSize);

        var warm = new ParticleSystem[prewarm];                 // pay the Instantiate cost NOW, during the fade
        for (int i = 0; i < prewarm; i++) warm[i] = pool.Get();
        foreach (var p in warm) pool.Release(p);
    }

    public void Burst(Vector3 at)
    {
        ParticleSystem p = pool.Get();                          // no allocation: an inactive instance is reused
        p.transform.position = at;
        p.Play();
        StartCoroutine(ReleaseWhenDone(p));
    }

    private IEnumerator ReleaseWhenDone(ParticleSystem p)
    {
        yield return new WaitForSeconds(p.main.duration + p.main.startLifetime.constantMax);
        pool.Release(p);                                        // back to the pool, not Destroy()
    }
}
using UnityEngine;
using UnityEngine.SceneManagement;

/// Ships in TEST builds only. Logs frames that overrun, tags the ones where the GC ran,
/// and refuses to flood the log — Debug.Log itself costs time and allocates.
public class FrameTimeWatchdog : MonoBehaviour
{
    [SerializeField] private float spikeMs = 25f;              // roughly two missed 72 Hz frames
    [SerializeField] private int maxLogsPerMinute = 20;        // a log budget: past this, stay silent
    private int logged, lastGcCount;
    private float windowStart;

    private void Update()
    {
        float ms = Time.unscaledDeltaTime * 1000f;             // unscaled: pause menus must not hide spikes
        if (Time.unscaledTime - windowStart > 60f) { windowStart = Time.unscaledTime; logged = 0; }
        if (ms < spikeMs || logged >= maxLogsPerMinute) return;

        int gc = System.GC.CollectionCount(0);                 // did a collection happen since last frame?
        bool gcRan = gc != lastGcCount;
        lastGcCount = gc;
        logged++;
        Debug.LogWarning($"[Watchdog] {ms:F1} ms frame at t={Time.unscaledTime:F1}s in "
                       + $"{SceneManager.GetActiveScene().name}{(gcRan ? " (GC ran)" : "")}");
    }
}

Read the watchdog's output with adb logcat -s Unity while the headset is on USB; the tag [Watchdog] makes it greppable. If most spikes say “GC ran,” you have an allocation problem and the profiler's GC Alloc column will find it. If they cluster at scene load, it is activation cost. If they are random, suspect the thermal governor — a hot Quest 3 clocks down, and a build that runs 72 fps cool can drop to 60 after fifteen minutes.

3. Bugs, triage, and what “release build” means

Bug

A difference between what the game does and what it was specified (or reasonably expected) to do. Write it as three lines: steps to reproduce, expected, actual, plus build version and device. “Teleport is weird” is not a bug report; “Teleport arc passes through the ruins gate and lands the player outside the boundary — 3/3 attempts, build 0.7.2” is.

Severity

How bad the consequence is when the bug happens: blocker (crash, cannot progress, comfort hazard), major (feature broken, workaround exists), minor (wrong but harmless), cosmetic. Severity is about impact, not about how ugly the code is.

Reproducibility

How reliably you can make the bug happen: always, sometimes (give a rate), once. A blocker you can reproduce is fixable tonight; a blocker you have seen once needs instrumentation (the watchdog, telemetry) before it can be fixed at all.

Triage

Sorting bugs by severity × frequency, adjusted for reproducibility, into a queue: fix now, fix before the playtest, fix before submission, won't fix. Triage is a team ritual, ten minutes at the start of each work session, with one person owning the list.

Release build

A build configured for players rather than developers: Development Build off, IL2CPP scripting backend, ARM64 only, Release C++ configuration, code stripping on, signed with your keystore, and a version code higher than the last build. It is smaller, faster, and — importantly — behaves slightly differently from a development build, so test it before presenting.

Stripping

Managed Stripping Level removes unused code from the build. Low is safe; Medium/High shrink the APK further but can strip code you only reach by reflection or JsonUtility (keep those types with a link.xml). If a release build crashes where the development build did not, suspect stripping first.

Keystore

1. A playtest is an experiment

Playtesting is the discipline of learning from players instead of from yourself. You are the worst possible tester of your own game: you know where the runes are, you have learned to avoid the teleport arc's bad spots, and you have not been motion-sick in the forest since Week 9 because you built it. Objective 2 asks for thorough playtesting, and thorough does not mean many hours — it means the sessions were designed so that what you observe can be trusted.

Playtest goal

The decision the test will inform, stated before the session: “decide whether the rune puzzle needs an extra hint,” “decide whether smooth locomotion can be the default.” A session without a goal produces a pile of opinions and no decision.

Hypothesis

A falsifiable prediction about what participants will do: “at least 8 of 10 first-time players solve the rune puzzle in under 3 minutes without a hint.” Writing the number down first stops you from moving the goalposts after the fact. Hypotheses can be wrong — that is the point.

Why it matters: Thursday's analysis is easy when there was a hypothesis and painful when there was not.

Participant

A person who plays your game under observation. Not a teammate, not someone who watched you build it. Record the attributes that plausibly change behavior: prior VR experience (none / some / regular), gaming experience, glasses, height, dominant hand, and whether they are prone to motion sickness.

Moderator

The team member who runs the session: reads the script, fits the headset, watches for discomfort, prompts think-aloud, and never helps unless the protocol says so. A second person observes and writes; the moderator cannot do both.

Think-aloud

Asking participants to narrate what they are trying to do and what they expect (“I'm going to grab this… oh, it didn't move”). It reveals mental models directly. It also slows people down and can suppress presence, so use it in usability sessions and switch it off in comfort or presence sessions.

Observation

A timestamped, factual note of something the participant did or said, tied to a location in the game: “02:14 — Ruins entrance — teleported into the wall twice, said 'where do I go'.” Interpretations (“was confused”) go in a separate column so you can argue about them later.

2. People, consent, and comfort

Recruit for diversity of experience, not for numbers. Five participants find most usability problems, and a first-time VR user finds different problems from a Quest owner. Aim for six to eight per team across the week: at least two who have never worn a headset, at least one who wears glasses, at least one who prefers to sit, and — if you can — one who is left-handed. Friends of teammates are acceptable if they have not seen the game; classmates from other teams are ideal.

Informed consent

Before the headset goes on, participants are told what will happen, how long it takes, what is recorded (screen capture, notes, no face video unless agreed), that they can stop at any time without giving a reason, and that VR can cause discomfort. They agree explicitly. Keep the form to one page.

Comfort stop rule

A rule you state aloud and then enforce: “If you feel warm, dizzy, or queasy, say 'stop' and we end immediately — that is useful data, not a failure.” Moderators also stop the session on their own if they see swaying, sweating, or a hand reaching for the headset. Nobody is asked to push through.

Why it matters: a participant who is made sick will not come back, and their data after the first symptoms is worthless anyway.

Moderation script

The exact words the moderator says: welcome, consent, headset fitting and IPD, the practice room, each task's prompt (“Find the guide and ask how to open the gate”), the standard non-answers (“What would you try?”), and the closing. Two moderators reading the same script produce comparable sessions.

Observation sheet

A prepared table with columns for timestamp, game location, event code (T = teleport problem, G = grab problem, N = navigation, C = comfort sign, Q = question asked, ! = delight), a factual note, and an interpretation column. Codes make counting on Thursday possible.

Interview technique

After the questionnaires: open questions first (“Tell me about the moment you felt most lost”), then specifics, and never leading (“Did you find the menu confusing?” → “How did you find opening the menu?”). Silence is a tool; count to five before rescuing a pause.

Pilot session

A dry run of the whole protocol with one participant to find the problems in the study — a task that cannot be completed, a script that takes twenty minutes, a build that lacks the telemetry logger. Today's activity is your pilot.

3. Telemetry: let the build take notes too

Telemetry is the observer that never blinks. While your human observer writes “seems lost,” the build records that the participant made 41 teleports in the ruins courtyard, opened the menu four times, and took 212 seconds on the rune puzzle with three failed attempts. Together they explain each other: telemetry says what, observation and interview say why.

public class Telemetry : MonoBehaviour
{

    [SerializeField] private Transform head;            // the XR Origin's Main Camera
    [SerializeField] private float sampleEvery = 0.5f;  // position rows per second = 2 (about 7 KB/min)
    private StreamWriter writer;
    private float nextSample;

    private void Awake()
    {
        if (I != null) { Destroy(gameObject); return; }  // singleton: one logger, ever
        I = this;
        string stamp = System.DateTime.Now.ToString("yyyyMMdd-HHmmss");
        string path = Path.Combine(Application.persistentDataPath, $"telemetry-{stamp}.csv");
        writer = new StreamWriter(path) { AutoFlush = true };   // flush per line: the app may be killed any time
        writer.WriteLine("t,event,scene,x,y,z,detail");
        Log("session_start", Application.version);
    }

    public void Log(string ev, string detail = "")
    {
        Vector3 p = head.position;
        writer.WriteLine($"{Time.unscaledTime:F2},{ev},{SceneManager.GetActiveScene().name}," +
                         $"{p.x:F2},{p.y:F2},{p.z:F2},{detail.Replace(',', ';')}");  // keep CSV columns intact
    }

    private void Update()
    {
        if (Time.unscaledTime < nextSample) return;
        nextSample = Time.unscaledTime + sampleEvery;
        Log("pos");                                       // heatmap data
    }

    private void OnDestroy() { writer?.Close(); }
}

4. Asking well: questionnaires and the reading

Behavior first, opinions second. After the tasks, participants complete short instruments before you talk to them, so the interview does not shape their answers. Use validated instruments where they exist; write your own items only for things specific to your game.

Questionnaire

A fixed set of items answered on a fixed scale, scored the same way for everyone. Its value is comparability: between participants, between builds, and against published norms. A questionnaire is only as good as its items; validated ones have been checked for reliability and meaning.

Likert scale

A statement (“I found the teleport arc easy to aim”) rated on an odd-numbered agreement scale, usually 5 or 7 points from strongly disagree to strongly agree. Mix positively and negatively worded items so straight-lining (ticking the same column) is detectable. Report medians and distributions; means of Likert items are common but treat them cautiously.

SUS (System Usability Scale)

Ten alternating positive/negative items, scored 0–100 (odd items: response − 1; even items: 5 − response; sum × 2.5). Average across products is about 68; above 80 is very good. It takes two minutes and works for VR games as well as for websites. Report the score per participant and the median.

SSQ (Simulator Sickness Questionnaire)

Sixteen symptoms (general discomfort, fatigue, headache, eye strain, sweating, nausea, dizziness…) rated 0–3, giving Nausea, Oculomotor, and Disorientation sub-scores and a total. Administer it before and after the session; the change is your comfort measurement. Any participant scoring “severe” on nausea is done for the day.

Presence questionnaire

Instruments that estimate the sense of “being there”: the IPQ (Igroup Presence Questionnaire: spatial presence, involvement, realness) is short and freely usable; the SUS-presence questionnaire (Slater–Usoh–Steed, unrelated to the usability SUS) asks six items about the extent to which the virtual place felt like a place visited. Use one; presence is the outcome your whole immersion budget was buying.

Custom items and open questions

Three to six Likert items about your specific design decisions (“The guide's voice was easy to locate”) plus two or three open questions (“What would you change first?”). Keep the whole post-session packet under ten minutes; tired participants satisfice.

1. From notes to themes: qualitative coding

Observation sheets and interview notes are qualitative data: rich, specific, and useless until organized. Qualitative coding is the organizing step. Each note gets one or more short labels — teleport-aim, menu-discovery, guide-inaudible — and labels that recur become themes. Do it as a team with the notes physically or virtually in front of you; the widget below is a small version of that board.

Qualitative coding

Assigning short labels to observations and quotes. Start open (invent codes as you read) then consolidate (merge synonyms: “couldn't find menu” and “looked at wrist” both become menu-discovery). Two people coding the same notes independently and comparing is the cheap way to check you are not seeing what you want to see.

Affinity mapping

Writing each observation on its own note and physically grouping notes that belong together, then naming the groups. The order matters: group first, name second, or you will sort the evidence into the categories you already believed in.

Theme

A named cluster of observations that describes one underlying problem or strength, with a count: “Players cannot tell which runes are already placed (7 notes, 5 participants).” A theme spans participants; one person's unique problem is an observation, not a theme.

Why it matters: objective 3 says common issues. The count per theme is what makes an issue common.

Triangulation

Confirming a finding with at least two independent sources: telemetry (what happened), observation (what it looked like), self-report (what it felt like). “Players said the puzzle was fine” (self-report) + “median 212 s with three fails” (telemetry) is a finding: the puzzle is harder than players admit, or they enjoyed the struggle — the interview decides which.

Root cause

The underlying reason a symptom occurs, found by asking why repeatedly (the “5 whys”): players teleport into the wall → the arc lands behind it → the wall has no collider on the teleport layer → the ruins prefab was made before the layer existed. The fix is the last answer, not the first.

Task completion rate

The share of participants who completed a task without moderator help, within the time limit. Report it as a fraction (7/9), not a percentage, when N is small — “78%” hides how few people you tested.

2. Summarizing the numbers honestly

With six to ten participants you are not doing inferential statistics; you are describing. Describe well: completion rate as a fraction, median task time (means are dragged by one lost participant), the interquartile range, and outliers named and explained rather than deleted. A box plot beside the raw dots is the honest picture. Enter your own data in the analyzer — drag a bar to set a participant's time, click the marker beneath to toggle whether they finished — and watch the mean and median disagree.

Task time

Seconds from the task prompt (or first interaction, for telemetry) to completion. Record failed attempts as the time at which you stopped them, flagged as incomplete; do not average them in as if they were successes.

Median and IQR

The median is the middle value; the interquartile range (Q3 − Q1) spans the middle half. Together they describe “typical” without being hijacked by one very slow or very fast participant. Report “median 84 s (IQR 61–140)”.

Outlier

A value far from the rest — conventionally beyond 1.5 × IQR above Q3 or below Q1. An outlier is a question, not noise: the 300-second participant is often the one who found the bug. Look them up in the observation sheet before deciding anything.

{

        for (int i = 0; i < 10; i++)

3. Deciding what to fix: prioritization

You will find more problems than you can fix in a week. Prioritization makes the choice explicit. The scheme below is a simplified RICE score (reach, impact, confidence, effort) adapted to a student team's week:

priority scoreP = impact · frequency · confidenceeffort

where impact is 1–5 (a comfort hazard is 5; a typo is 1), frequency is the share of participants affected (from your theme counts), confidence is 0.5–1 (how sure you are of the root cause), and effort is person-days. A score is not a decision — a comfort hazard with a low score still gets fixed — but it stops the loudest teammate's pet issue from silently going first.

Impact

How much the player experience improves if this issue is fixed, for the players it affects. Comfort and progression blockers are maximal; delight and polish items are real but lower.

Frequency

The proportion of participants who hit the issue, straight from the affinity counts. Multiply by impact and a rarely-seen blocker can rank below a universally-seen annoyance — which is often right for a one-week window.

Effort

Honest person-days to implement and test the change, including the regression risk (a change to the teleport layer touches every scene). Double it if nobody on the team has done it before, as in Week 2.

Refinement

A change defined as a testable before/after statement: “Add a glowing outline to placed runes so that first-time players solve the rune puzzle in under 120 s (currently median 212 s).” The number after “so that” is how you will know on Tuesday whether it worked.

Regression risk

The chance a fix breaks something that worked. Rank fixes by it as well as by score; batch risky fixes early in the week so there is time to retest, and keep the last two days for safe ones.

Findings report

One page: goal and hypotheses; who was tested (N, experience mix); method (tasks, instruments); results (completion table, median times, SUS/SSQ medians, top themes with counts); prioritized refinements with before/after targets; limitations. Three habits make late changes survivable.

Refinement branch

One branch per refinement (refine/rune-placed-glow), merged into integration only after someone other than the author plays the affected scene on a Quest 3. Small branches merge cleanly and revert cleanly; “fixed lots of stuff” commits do neither.

Feature flag

A boolean (in a settings ScriptableObject or PlayerPrefs) that switches a change on or off at runtime without a rebuild. New teleport arc behind flags.newArc: if the retest goes badly, flip it off; if it goes well, delete the old code after the presentation, not before.

Why it matters: a flag turns a risky change into a reversible one, and lets you demo the old and new behavior in the same build on Thursday.

A/B in builds

Two builds (or one build with a flag) given to alternating participants so the same protocol compares old and new. With four retest participants you will not get statistics, but you will see whether the median moved in the right direction and whether anything new broke.

Content lock

A date after which no new content, features, or assets enter the build — only bug fixes and tuning. For Milestone 7, content lock is tonight. Everything you wanted but did not finish goes into the presentation's “future work” slide, where it is worth points; unfinished in the build, it is worth bugs.

Definition of done

The checklist an item must pass to be called finished: works on device in a release build, survives a scene transition and a save/load, has feedback (sound + visual + haptic), has been played by someone other than its author, is in the GDD. Write yours down; “done” without a definition means “I stopped.”

    {

        continuousTurnProvider.SetActive(!s.snapTurn);
        vignetteController.SetActive(s.vignette);

        // Seated mode: Device origin (height comes from the rig, not the floor) + a fixed eye height.
        origin.RequestedTrackingOriginMode = s.seatedMode ? XROrigin.TrackingOriginMode.Device

        if (s.seatedMode) origin.CameraYOffset = seatedEyeHeight;
    }

    public void Recenter(Transform anchor)
    {
        origin.MoveCameraToWorldLocation(anchor.position + Vector3.up * origin.CameraInOriginSpaceHeight);
        origin.MatchOriginUpCameraForward(anchor.up, anchor.forward);

2. Accessibility and inclusive design

Accessibility is whether a player who is seated, one-handed, colorblind, hard of hearing, or new to VR can play your game. Inclusive design is the habit of asking that question in Week 2 rather than Week 15. You are asking it in Week 15, which is late but not too late: most of the items below are options you already half-built in Topics 4–6, and the syllabus names accessible and inclusive content as the skill this milestone showcases.

Seated mode and height recenter

Many players cannot or prefer not to stand. Seated mode sets a fixed eye height, keeps every reachable object within a seated arm's reach, and provides a recenter action that moves the world so the player faces the right way. Test it: sit in a chair and play your rune puzzle. Can you reach the top rune?

One-handed and left-handed modes

Left-handed: swap the move/turn sticks and the dominant-hand ray. One-handed: every action reachable from a single controller — the menu button, teleport, and grab must not require two hands, and puzzles must not require holding two objects simultaneously (or must offer a socket to park one).

Comfort preset

A one-touch choice on first launch — Comfortable (teleport, snap turn, vignette), Moderate, Intense (smooth everything) — with the safe option preselected, from Topic 5. Presets are inclusive because they do not require the player to understand what a vignette is before choosing.

Subtitles / captions

Text for all dialogue (subtitles) and for meaningful sounds (captions: “[waterfall to the left]”). World-locked near the speaker or lazily following the view at 1.5–2 m, large enough to read at about 25 pixels per degree, with a speaker label. They serve deaf and hard-of-hearing players, non-native readers, and everyone in a noisy lab.

Colorblind-safe cues

About 8% of men and 0.5% of women have a red–green color vision deficiency. A rune puzzle that distinguishes runes by red vs green alone excludes them. Rule: never encode meaning in hue alone — add shape, pattern, position, label, or sound. Test with a simulator (below) and with a colorblind-safe palette.

Adjustable text size and contrast

A text-scale slider (0.8–1.6×) applied to the panel root, and light text on a dark, semi-opaque panel (contrast ratio ≥ 4.5:1). A small change that helps players with low vision and players with older lenses alike.

Audio-only mode as an inclusive feature

The dark mode you built in Topic 6 — navigating Elaria by sound alone — is also a design probe for blind and low-vision players: if the game can be played with the world black, its audio guidance is strong enough for everyone. Present it that way.

Pause anywhere, no time pressure by default

Cognitive and motor accessibility: the pause menu opens from every state, dialogue never auto-advances, puzzles have no timers unless the player opts in. Anxiety is an accessibility issue too.

2. Demoing VR live without the demo becoming the story

A live VR demo has a failure mode no slide deck has: one person is blind to the room, the audience sees a shaky mirror of their view, and the battery, the Wi-Fi, and the guardian all have opinions. Professionals do it anyway because a live demo is more convincing than any video — but they prepare for it as a stunt.

Casting

Mirroring the headset view to a screen. On Quest 3: the Cast option in the headset's quick settings to a browser or the phone app, or a USB cable with scrcpy / the Meta Quest Developer Hub for a lower-latency, higher-quality feed. Test it in the presentation room on the room's screen, not in the lab.

Driver and narrator

Two people: one plays (the driver), one talks (the narrator) facing the audience. The driver cannot see the audience or the timer; the narrator keeps the story going while the driver walks the rehearsed path. Never present alone from inside the headset.

Rehearsed path

A fixed route through the game that shows the most in the least time and avoids every known bug. Walk it three times the day before and once in the room. Improvisation is for the Q&A.

Backup video

A 3–4 minute capture of the rehearsed path, on a laptop that is already plugged into the projector, cued to the start. If the cast drops or the build crashes, the narrator says “let me show you the same run” and the presentation continues without a gap. Half the class will use it; that is fine.

Hardware readiness

Both headsets charged above 80% (a Quest 3 lasts about two hours of play), both controllers with fresh batteries, the guardian set up in the presentation space, the release build installed on both, the Wi-Fi not required by the build at all.
